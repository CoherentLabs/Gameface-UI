    Typed inline styles (CSSTOM)

    In version 4.2.0, Gameface UI introduced the Style TOM plugin and CSSTOM style runtime library that can automatically detect and rewrite reactive numeric style values, applying them through Gameface’s CSS Typed Object Model, improving performance and reducing runtime parsing overhead.

    How it works

    Section titled “How it works”

    The plugin and runtime library are located in scripts/babel/style-tom-plugin.mts and src/components/BaseComponent/gameface-dom.ts respectively.

    The plugin is responsible for detecting reactive numeric style values in your Solid components and rewriting them into a structured format that the runtime can understand and then apply them efficiently using CSSTOM.

    This allows you to keep writing normal Solid styles. When a style changes reactively, the Style TOM plugin (scripts/babel/style-tom-plugin.mts) looks for supported numeric values before Solid compiles the JSX. For example, this authored style:

This fast path is used only when the property is supported and the element exposes attributeStyleMap - see Supported properties. The opacity number in this example also uses CSSTOM, without needing a unit. Values that are not eligible continue through the normal inline-style path that Solid normally uses.

    Section titled “Setup”

    Both pieces are registered through vite-plugin-solid in vite.config.mts - the plugin as a Babel plugin, the runtime through Solid’s moduleName option:

    The plugin and runtime have no options to configure. Detection is conservative: when the plugin cannot confidently recognize a value, it leaves it alone rather than guessing.

    Existing projects

    If your project was created before 4.2.0, update your components first, then add the config above:

    The updated BaseComponent brings everything the plugin needs: the style runtime (src/components/BaseComponent/gameface-dom.ts) and the plugin files in scripts/babel/. The plugin also rewrites styles you pass to Gameface UI components, so they need this updated BaseComponent - don’t enable the plugin on an older one.

    The plugin checks this for you. If the style runtime is missing, doesn’t match the plugin’s version, or BaseComponent doesn’t use it, the plugin rewrites nothing and prints a warning telling you to run gameface-cli update - your UI builds exactly as it would without the plugin. If Solid’s moduleName doesn’t point to the style runtime, the build stops with an error showing the line to add, because the rewritten styles would not work.

    Supported properties

    Section titled “Supported properties”

    Only properties Gameface documents as CSSTOM-eligible use it. Everything else (colors, display, shorthands like margin, padding, border, background, font, flex, transition, animation, outline, and custom properties) is applied as an ordinary style:

    • Position: top, left, right, bottom
    • Size: width, height, min-width, min-height, max-width, max-height
    • Margin: margin-top, margin-right, margin-bottom, margin-left
    • Padding: padding-top, padding-right, padding-bottom, padding-left
    • Border width: border-top-width, border-right-width, border-bottom-width, border-left-width
    • Flex: flex-basis, flex-grow, flex-shrink
    • Text: font-size, letter-spacing, line-height, text-decoration-thickness, text-stroke-width, text-underline-offset
    • Other: opacity, z-index

    Section titled “Transforms”

    The plugin supports translate(), scale(), rotate(), skewX(), and skewY() in a transform template literal or string concatenation:

    Caution

    Gameface doesn’t support the combined skew() function, so use skewX() and skewY() instead. A value containing skew() isn’t rewritten, and Gameface ignores it:

    The value is rewritten only if every function in it can be rewritten. Otherwise the entire value stays a plain CSS string:

    • Every function must be one of the five above. Other functions Gameface supports, such as translateX(), translateY(), scaleX(), scaleY(), rotateZ(), translate3d() and matrix(), still work, but the plugin doesn’t rewrite them so the value remains a plain CSS string.
    • translate() takes values in px, %, vw, vh, vmin, vmax, em, rem or pt. rotate() and the skew functions take deg - the only angle unit Gameface supports. scale() takes plain numbers.
    • As with other properties, a missing unit is not guessed. Only a literal 0 may be written without one:

    Functions are applied in the order you write them, and a function can be used more than once, exactly as in a plain CSS string:

    Each value is rewritten to an object listing the functions in order and the numbers to apply (see Writing a transform by hand for how the object works):

    On every update the runtime only changes the numbers that moved. The order is fixed by your source code, so it’s set up once per element.

    Values that stay on the normal style path

    Section titled “Values that stay on the normal style path”

    Values that the plugin cannot safely recognize are still valid styles. They continue through Solid’s ordinary inline-style handling, which updates the style when the reactive value changes. For example, colors and CSS keywords are not numeric CSSTOM values:

    A supported property also stays on that path if the plugin cannot see the number and unit together. For example, a prebuilt string passed as the whole property value is not rewritten:

    Likewise, a template literal with no unit is left alone; the plugin does not guess that the value should be in pixels:

    The plugin also leaves values it cannot safely trace, such as props.style, spreads, computed property names, reassigned bindings, and helpers with multiple conditional returns. A spread only hides the properties it provides; adjacent properties can still be rewritten:

    Fully static styles are left for vite-solid-style-to-css, which moves them into a CSS class. A number for a property that takes a unit (width, left, margin-top, …) should come with its unit; in typed code, use the { value, unit } shape. For example, style={{ width: { value: w(), unit: 'px' } }}. If a plain number reaches such a property from untyped code, the runtime treats it as pixels.

    Writing a transform by hand

    Section titled “Writing a transform by hand”

    A transform has its own object shape, { functions, values }. It’s what the plugin produces from a transform string, and you can write it yourself too - for example when the numbers come from props:

    The syntax has been designed in this way to optimize the handling of dynamic transform values in a structured and predictable way and reduce unnecessary recalculations and comparisons at runtime so you get the most performant update.

    Think of it as a CSS transform string split in two:

    • functions is the transform with the numbers taken out. Every place a number was, you write only its unit.
    • values is the numbers that were taken out, in the same order.

    So translate(10px, 20px) rotate(45deg) becomes:

    More examples:

    CSS stringfunctionsvalues
    translate(10px, 20px)'translate(px,px)'[10, 20]
    translate(10px)'translate(px)'[10] - Y is 0, as in CSS
    translate(-50%, 10vh)'translate(percent,vh)'[-50, 10]
    scale(2)'scale(number)'[2]
    scale(2, 0.5)'scale(number,number)'[2, 0.5]
    rotate(45deg)'rotate(deg)'[45]
    skewX(10deg) skewY(5deg)'skewX(deg) skewY(deg)'[10, 5]
    rotate(45deg) translate(100px)'rotate(deg) translate(px)'[45, 100]
    translate(50px) translate(30px)'translate(px) translate(px)'[50, 30]

    Rules:

    • Supported functions: translate() and scale() with one or two arguments, rotate(), skewX() and skewY() with one.
    • Units: px, percent (for %), vw, vh, vmin, vmax, em, rem and pt for translate(); deg for rotate(), skewX() and skewY(); number for scale(), which has no unit.
    • values needs exactly one number per unit in functions.
    • An entry in values can be a number or a signal, e.g. values: [x, y] instead of values: [x(), y()].
    • Functions are applied in the order written, and the same function can appear more than once.

    Keep functions the same between updates and change only values - that’s the fast path, since only the numbers that changed are written. Changing functions (for example switching from px to %) also works, but rebuilds the element’s transform. A functions string with anything else in it, such as rotateZ(deg), is applied as a plain CSS string instead of through CSSTOM - so a typo produces invalid CSS, which Gameface ignores.
