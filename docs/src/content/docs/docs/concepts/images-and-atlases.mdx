The template includes an images plugin that does two things: it exposes files from `src/assets` as `Image.folder.name`, and it can pack the images a view actually uses into texture atlases during the build.

This page covers the build side only. The authoring API is documented on the [`Image` component page](/components/media/image/).

## What the plugin does

During the build, `Image.icons.gamepad.xbox.a` is rewritten to the real asset file. That lets the bundler see exactly which images each view can reach.

When atlas generation is enabled, the plugin packs those images into one or more PNG sheets and writes a lookup object into the view entry file:

```js
window.__GF_ATLAS__ = {
  "a-DYLBUbVy.png": { image: "url(../assets/atlas-menu-icons-D0x.png)", size: "…", position: "…" },
  …
};
```

`Image` looks up its filename in that object. If it finds a match, it renders the sprite; otherwise it falls back to the normal file. In development, there is no atlas at all, so every image is just a regular asset.

## Why atlas images

The benefit is not smaller file size. The win is fewer GPU textures and fewer texture switches:

- **Fewer textures at load.** Thirty icons become one sheet, so the engine allocates one texture instead of thirty. Gameface's own profiling guidance names loading sprite frames as separate images as a common cause of texture thrashing, where textures are created and destroyed repeatedly.
- **Fewer texture binds while drawing.** Elements sharing a sheet can be drawn together rather than each switching to its own texture.
- **Something you can preload.** This is the part worth the effort. Warming a handful of sheets before a view opens is practical; doing the same for fifty individual files is not. Once the build is producing sheets you are happy with, they are ordinary PNGs in `dist/assets` that your integration can load up front, so opening the view costs no texture allocation at all.

This is a tradeoff: a sheet may use more texture memory than the individual files, but it cuts texture churn and startup cost.

## Configuration

The plugin is registered in `vite.config.mts`:

```ts
gamefaceImages({
  assets: resolve(__dirname, 'src/assets'),
  types: resolve(__dirname, 'src/components/Media/Image/ImageTypes.ts'),
  atlas: ['icons/hud'],
});
```

| Option | Description |
|---|---|
| `assets` | Folder whose images are exposed on `Image`. |
| `types` | Where the generated types are written. |
| `atlas` | Which images to pack, as groups. Omit it and nothing is packed. |
| `atlasDefaults` | Base settings used by every group. |
| `verbose` | Adds detailed sprite positions to the build report. |

The generated types file is rewritten on every build and during dev. It describes the shape of your `src/assets` tree, which makes `Image.icons.gamepad.xbox.a` autocomplete and fail at compile time if you mistype it.

<Aside type="note">
Atlassing is opt-in. Without `atlas`, the plugin still provides the `Image.*` syntax and generated types, but every image ships as an individual file.
</Aside>

## Groups and matching

Each entry in `atlas` describes one sheet. A plain string is a folder shorthand:

```ts
atlas: ['icons/hud']; // same as { include: 'icons/hud/**' }
```

Use an object for custom rules:

```ts
atlas: [
  'icons/hud',
  {
    include: 'icons/gamepad/**',
    exclude: 'icons/gamepad/ps5/**',
    name: 'glyphs',
    padding: 4,
  },
  '**', // catch-all for any remaining images
],
atlasDefaults: { squareCells: true },
```

Important rules:

- patterns are relative to `assets`
- first matching group wins
- put specific groups first and catch-alls last
- a group that matches nothing in any view logs a warning

## Key settings

| Setting | Default | Why it matters |
|---|---|---|
| `maxWidth` / `maxHeight` | `2048` | Largest sheet size before a second sheet is created. |
| `padding` | `2` | Adds transparent spacing to avoid bleeding at fractional scale. |
| `pot` | `true` | Rounds sheet sizes up to the next power of two. |
| `squareCells` | `false` | Reserves a square cell so sprites render like `contain` + `center`. |
| `maxSpriteSize` | `2048` | Larger sprites are not packed. |
| `keepOriginals` | `false` | Keeps the standalone file beside the atlas version. |

When `pot` is enabled, the packer rounds up first and only then checks the maximum. Use power-of-two values for the max dimensions.

## Which images get packed

An image is packed only if all of these are true:

- written as `Image.folder.name`
- not given an `options` prop
- matches a group and is not excluded
- not larger than `maxSpriteSize`

If any rule fails, the image stays a normal file. The build report lists it under `skipped` with the reason.

<Aside type="caution" title="Two cases the plugin cannot detect">
The `options` rule is enforced only when the plugin can read the props. It cannot see values passed through runtime merges or dynamic access, such as:

```jsx
<Image.icons.hud.weapon {...rest} />
// OR
const glyphs = { a: Image.icons.gamepad.xbox.a };
<Dynamic component={glyphs[key()]} />
```

Those images still get packed. If you pass `options` that way, set `keepOriginals: true` on the group.
</Aside>

## Read the build report

The report is the main troubleshooting tool. It tells you which sheets were created, how many sprites fit, and which images were skipped.

```
Hud
  icons-hud        1024x1024     4 sprites    34% used
  glyphs           1024x512      3 sprites    69% used
  skipped  weapon2.png   768x271 > maxSpriteSize 512 ("glyphs")
```

The important number is the GPU texture memory estimate, not the disk size. A 1024x1024 sheet is roughly 4 MB of RGBA8 memory even if it is mostly empty. In practice, you want fewer large sheets that are still efficient enough to justify the trade.

## Limitations

- `Image` does not work inside `cohinline` or `InlineTextBlock`; use a plain `<img>` there.
- CSS background images cannot be looked up in the atlas.
- `Image.icons.gamepad.ps5[key]` pulls in the whole folder.
- sprites are positioned as percentages, so higher `padding` may be needed at fractional scales.
